# Decisions log (เพิ่มต่อท้ายเท่านั้น)

รูปแบบ: `## D-<เลข> — <หัวข้อ>` • วันที่ • ผู้ตัดสินใจ • อ้างอิง • การตัดสินใจ • เหตุผล • ผลกระทบ
ถ้าเปลี่ยนใจ ให้เพิ่มรายการใหม่ที่อ้างถึงรายการเดิม (เช่น "แทนที่ D-003") ห้ามแก้ของเก่า

## D-001 — Feature เป็นปลั๊กอินที่โหลดอัตโนมัติ
- วันที่: 2026-10-24 • ผู้ตัดสินใจ: ผู้สอน • อ้างอิง: `apps/api/src/features/index.js`, `docs/features.md` หัวข้อ 2
- การตัดสินใจ: ทุก feature อยู่ใน `apps/api/src/features/<ชื่อ>/index.js` และ export `path`, `routes`, `repository` — ระบบโหลดเอง
- เหตุผล: 5 กลุ่มทำงานพร้อมกัน ถ้าทุกคนต้องแก้ `app.js` จะชนกันตอน merge
- ผลกระทบ: ห้ามแก้ `app.js`, `features/index.js`, `repositories/postgres.js` เพื่อเพิ่ม feature

## D-002 — Feature ของกลุ่มใช้ Postgres เท่านั้น
- วันที่: 2026-10-24 • ผู้ตัดสินใจ: ผู้สอน • อ้างอิง: `docs/postgres.md`
- การตัดสินใจ: feature ใหม่เขียน repository สำหรับ Postgres อย่างเดียว ไม่ต้องทำเวอร์ชัน memory — โหมด `memory` ตอบ 501
- เหตุผล: ต้องการให้ข้อมูลอยู่หลัง restart และได้ฝึก SQL จริง
- ผลกระทบ: ต้อง `npm run db:up` และ `npm run db:setup` ก่อนเริ่ม · เทสต์ของ feature ต้องตั้ง `TEST_DATABASE_URL`

## D-003 — ช่วงเลข migration แยกตามกลุ่ม
- วันที่: 2026-10-24 • ผู้ตัดสินใจ: ผู้สอน • อ้างอิง: `docs/features.md` หัวข้อ 3
- การตัดสินใจ: กลุ่ม 1 `110–129` · 2 `130–149` · 3 `150–169` · 4 `170–189` · 5 `190–209` · ต่ำกว่า `110` เป็นของส่วนกลาง
- เหตุผล: `migrate.js` รันตามลำดับชื่อไฟล์ ถ้าเลขชนกันจะ merge ไม่ได้หรือรันผิดลำดับ
- ผลกระทบ: ห้ามแก้ migration ที่ merge แล้ว ให้เพิ่มไฟล์เลขถัดไปในช่วงของกลุ่ม

## D-004 — Login ใช้ JWT ใน HttpOnly cookie กับบัญชีตัวอย่าง ไม่มีหน้าสมัครสมาชิก
- วันที่: 2026-10-24 • ผู้ตัดสินใจ: ผู้สอน • อ้างอิง: `apps/api/src/middleware/auth.js`, `docs/features.md` หัวข้อ 1
- การตัดสินใจ: ใช้ `requireAuth(config)` / `requireRole(...)` ที่มีอยู่ · บทบาทมี `staff`, `head`, `admin` · บัญชีใหม่สร้างผ่านกลุ่ม 5 โมดูล A เท่านั้น
- เหตุผล: ไม่ให้ทุกกลุ่มเขียนระบบ login ซ้ำ และสอนได้ในเวลาจำกัด
- ผลกระทบ: ห้ามสร้าง middleware ตรวจสิทธิ์ของตัวเอง · ระบบจริงต้องเปลี่ยนเป็น SSO ของมหาวิทยาลัย

## D-005 — กลุ่มคุยกันผ่าน API ไม่ JOIN ตารางข้ามกลุ่ม
- วันที่: 2026-10-24 • ผู้ตัดสินใจ: ผู้สอน • อ้างอิง: `docs/features.md` "สัญญาระหว่างกลุ่ม"
- การตัดสินใจ: ตารางเป็นของกลุ่มเจ้าของ กลุ่มอื่นอ่านผ่าน endpoint ที่เจ้าของเปิดไว้ · หน้า Public เสียบผ่าน `PUBLIC_SECTIONS`
- เหตุผล: เจ้าของเปลี่ยน schema ได้โดยไม่ทำให้กลุ่มอื่นพัง
- ผลกระทบ: ถ้าต้องใช้ข้อมูลกลุ่มอื่น ให้ตกลง endpoint และรูปแบบ JSON แล้วบันทึกเป็น Decision ใหม่

## D-006 — Upload ไฟล์และ Audit log เป็นของส่วนกลาง
- วันที่: 2026-10-24 • ผู้ตัดสินใจ: ผู้สอน • อ้างอิง: `docs/features.md` หัวข้อ 1 (รายการ ⏳)
- การตัดสินใจ: ทีมไม่สร้างตาราง upload หรือ audit เอง · ก่อนส่วนกลางพร้อม ให้เก็บเอกสารเป็น `url` (http/https)
- เหตุผล: เกือบทุก feature ต้องใช้ ถ้าแต่ละกลุ่มเขียนเองจะได้ 3–4 แบบที่ไม่เข้ากัน
- ผลกระทบ: เมื่อส่วนกลางพร้อม ผู้สอนจะเพิ่ม Decision ใหม่ระบุชื่อฟังก์ชันและวิธีเรียก

## D-007 — แบ่งงานในกลุ่มตามโมดูล (แนวตั้ง)
- วันที่: 2026-10-24 • ผู้ตัดสินใจ: ผู้สอน • อ้างอิง: `docs/features.md` "วิธีแบ่งงาน 4 คนในกลุ่ม"
- การตัดสินใจ: 1 คน = 1 โมดูล ทำครบ migration + API + หน้าจอ + เทสต์ · มี "ผู้ประสาน" ผลัดกันดูแล `lib/features.js` และการ merge
- เหตุผล: ไม่ต้องรอกัน และทุกคนได้ฝึกทุกชั้น
- ผลกระทบ: ไฟล์ร่วมของกลุ่มแก้โดยผู้ประสานเท่านั้น
